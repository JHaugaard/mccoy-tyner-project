# Data Pipeline SOP — jazz-canon-site data refresh

How the static JSON consumed by `jazz-canon-site/data/` gets produced and
enriched, who owns each step, and the order they must run in. Keep this
current — it's the operating manual. **Both scripts now run from mccoy-tyner**
(migrated 2026-07-01 — see status below) but write their output across into
the sibling `jazz-canon-site` repo, which is the one that actually deploys.

## The one-liner

`export.py` rebuilds the album JSON from the Postgres DB; `apple_previews.py`
then layers 30-second Apple Music preview URLs on top. The site serves the
resulting committed JSON as static assets — no database at runtime.

## Script ownership

| Script | Owner / home | Produces | Status |
|--------|--------------|----------|--------|
| `export.py` | **mccoy-tyner** (the data platform, SSOT) | `../jazz-canon-site/data/albums.json`, `data/album/*.json`, `data/network.json`, `data/musicians.json` | ✅ Migrated 2026-07-01 — physically lives in `mccoy-tyner/scripts/` now. |
| `apple_previews.py` | **mccoy-tyner** | adds `preview_url` (+ backfills `apple_track_id`) to `../jazz-canon-site/data/album/*.json` | ✅ Migrated 2026-07-01 alongside `export.py` — kept together since both write into the site's `data/` and share the run-order dependency below. |

Why split conceptually (even though both scripts now live in the same repo):
album/personnel facts are source-of-truth and belong to the data platform.
Apple preview URLs are volatile `mzstatic` CDN links — a **cache**, not a
fact — so enrichment is a separate, re-runnable step layered on top.

Both repos live side by side on the same box (`~/dev/active/mccoy-tyner` and
`~/dev/active/jazz-canon-site`) — the `--output-dir`/`--data-dir` flags below
just point across that sibling boundary.

## Run order (this matters)

`export.py` regenerates the album JSON **from scratch**, which **wipes
`preview_url`**. Run both from `mccoy-tyner/`:

```
1. .venv/bin/python3 scripts/export.py \
     --output-dir ../jazz-canon-site/data        # rebuild data/ from the DB
2. .venv/bin/python3 scripts/apple_previews.py \
     --data-dir ../jazz-canon-site/data/album     # re-add preview URLs
3. cd ../jazz-canon-site && git add data/ && git commit && git push   # publish to site
```

If you only edited the DB and re-ran export, you MUST re-run apple_previews or
every play button disappears. If you only want to refresh previews (e.g. a
stale CDN link), step 2 alone is fine.

### Useful flags for `apple_previews.py`

```
--dry-run            # show matches + coverage, write nothing (always do this first)
--album <slug>       # just one album, e.g. --album andrew-hill-black-fire
--limit N            # first N albums only
```

## Secrets

- Apple credentials live in `mccoy-tyner/.env.local` (gitignored):
  `APPLE_MUSIC_TEAM_ID`, `APPLE_MUSIC_KEY_ID`, `APPLE_MUSIC_PRIVATE_KEY_PATH`,
  `APPLE_MUSIC_STOREFRONT`. These moved here from `jazz-canon-site/.env.local`
  as part of the 2026-07-01 migration — jazz-canon-site's copy is stale, don't
  edit it.
- The MusicKit private key is `mccoy-tyner/secrets/AuthKey_<KEYID>.p8` —
  **never committed** (`secrets/` and `*.p8` are gitignored). If it ever
  leaks, revoke the key in the Apple Developer portal and generate a new one.
- The developer token used by `apple_previews.py` is a short-lived (~1 h) ES256
  JWT generated **in memory at run time** — never written to disk or shipped to
  the browser. Nothing to rotate for this step.
- Full playback (Step 3 in the site) uses a separate *client-side* developer
  token baked into the site's build (`PUBLIC_APPLE_DEV_TOKEN`), generated by
  `scripts/gen_dev_token.py` (also now here in mccoy-tyner). It has a ~6-month
  max lifetime — **rotation is a recurring chore**, fully documented in
  **[apple-token-rotation.md](apple-token-rotation.md)**. Note the extra
  cross-repo step this migration introduced: the token is written to
  `mccoy-tyner/.env.local` by the script, but the site's *build* needs it in
  `jazz-canon-site/.env.local` (local dev) or the Cloudflare Pages build env
  (prod) — copy the value across manually after regenerating.

## Playback UX contract

The site **never renders a dead play button**:
- no `preview_url` → no button (aligned empty slot, not a broken control)
- a `preview_url` that fails at runtime → the button removes itself after the
  failed click (see `src/lib/stores/preview.js` → `brokenPreviews`)
